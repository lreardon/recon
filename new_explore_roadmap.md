# New Exploration System Roadmap

A plan for rebuilding the exploration loop so that (1) no pair is ever explored twice, (2) no
nullary is ever evaluated twice, and (3) the FSTs are updated incrementally as exploration runs, so
every lookup stays fast and every restart resumes exactly where it left off.

## Where we are today

The current loop lives in `ruby/models/explorer.rb`, driven interactively from `ruby/explore.rb`:

1. **Enumerate pairs.** At depth *d*, phase 1 pairs new nullaries (`state/chains/nullaries/d.txt`)
   against all unary files `0..d`; phase 2 pairs old nullaries `0..d-1` against new unaries
   (`state/chains/unaries/d.txt`).
2. **Generate candidates.** Each `(unary, nullary)` pair produces one candidate nullary
   (`unary.sub('*', nullary)`) and two candidate unaries (`R(u#,nullary,*)`, `R(u#,*,nullary)`),
   appended to `candidates/*.txt`.
3. **Batch process.** Every 500 pairs (`SAVE_MODULUS`): dedup the candidate files with `.uniq`,
   evaluate candidate nullaries in ruby, merge results into `fst/evaluations.fst` and
   `fst/unaries.fst` via the rust merge binaries, append candidates to next depth's chain files,
   clear candidate files, checkpoint `state/progress.json`.

### Why it repeats work

- **Candidates are evaluated before being checked against the FST.** `evaluate_candidate_nullaries`
  evaluates everything in the batch; the `check_candidates_against_fst` step is commented out. Any
  candidate that already exists (generated by a different pair, or in a previous run) is fully
  re-evaluated.
- **Evaluation itself is slow and forgetful.** The ruby evaluator shells out one subprocess per FST
  query and only queries at recursive depth ≥ 2. Its memo table dies with the process, and
  intermediate subexpression values it computes along the way are never written back to the FST.
- **Checkpoint granularity ≠ batch granularity.** Progress saves every 500 ticks but candidates
  accumulate continuously, so a crash mid-batch replays up to 500 pairs, re-generating and
  re-evaluating their candidates.
- **Chain files can accumulate duplicates.** `save_chains_from_candidates` dedups within a batch
  (`.uniq`) but not against earlier batches or earlier depths, so the same expression can appear in
  multiple chain files and be paired repeatedly at later depths.
- **Full FST rewrite per batch.** Each merge streams a union of the whole base FST plus the delta
  into `tmp_n.fst`/`tmp_u.fst`, then copies over the base. At 500-pair batches this rewrite cost is
  paid constantly and grows with the base.

## Target architecture

Move the hot loop into a single rust binary (`explore`), reusing the fast evaluator already built in
`rust/evaluations/src/bin/compute/evaluate_recursive_form.rs`. Ruby remains available as the
interactive front-end (shelling out to the rust engine), but no evaluation or dedup logic stays in
ruby.

```
┌─────────────────────────── explore (rust) ────────────────────────────┐
│                                                                       │
│  Pair enumerator ──► Candidate generator ──► Dedup gate ──► Evaluator │
│  (depth/phase/index)   (subst templates)     (memo+FST)     (memoized,│
│        │                                        │            closed-  │
│        │                                        ▼            form)    │
│        │                                   skip if known        │     │
│        ▼                                                        ▼     │
│  progress.json  ◄────────── batch commit ◄──────── new (key, value)   │
│  (written atomically        - build delta FST                         │
│   AFTER fst merge)          - union-merge into base (atomic rename)   │
│                             - append chain files                      │
└───────────────────────────────────────────────────────────────────────┘
```

### 1. Never evaluate the same nullary twice

- **Check before evaluating, at three tiers:** in-memory memo (this run) → base FST (all past
  runs) → pending-batch set (evaluated this batch, not yet merged). Only a miss at all three tiers
  triggers evaluation. This is the single biggest work-saver and is nearly free once the FST is
  in-process (`load_evaluations()` is already memory-mapped via `lazy_static`).
- **Write back subexpression values.** The evaluator computes values for every nullary
  subexpression it touches (bases, countdowns, unary constants). Collect all of these into the
  pending batch, not just the top-level candidate, so deep forms encountered later start from
  precomputed parts.
- **Unaries dedup the same way** against `fst/unaries.fst` plus a pending set (membership only; it
  is a Set, not a Map).

### 2. Never explore the same pair twice

- **Deterministic enumeration order.** Keep the depth/phase/file-index/item-index scheme, but make
  the ordering a documented invariant: chain files are append-only and immutable once a depth is
  closed, so `(depth, phase, nullary_file, nullary_idx, unary_file, unary_idx)` names a unique pair
  forever.
- **Checkpoint after commit, atomically.** Write `progress.json` only after a batch's FST merge and
  chain-file appends have landed, via write-to-temp + rename. On restart, resume from the recorded
  cursor. Because dedup (tier 1–3) makes replay idempotent *and* the cursor never points into an
  uncommitted batch, a crash costs at most one batch of cheap membership checks and zero
  re-evaluations.
- **Dedup chain appends globally.** Before appending a candidate to the next depth's chain file,
  check it against the FSTs (for nullaries: was it already known? for unaries: already in the set?).
  A known expression was already scheduled for pairing at the depth where it first appeared —
  appending it again is what causes duplicate pairing today. With this gate, every expression is
  paired exactly once, at its first-discovery depth.

### 3. Update FSTs incrementally without rewriting the world

The `fst` crate's structures are immutable, so "incremental" means layering, not in-place writes:

- **Batch → delta FST → union merge.** Keep the existing union-merge approach
  (`merge_new_nullaries_evaluated_json_into_evaluations_fst.rs` already does this) but do it
  in-process: sort the pending batch, `MapBuilder::memory()` a delta, stream the union into
  `fst/evaluations.fst.tmp`, then **atomic `rename`** (not `fs::copy`) over the base. A crash
  mid-merge leaves the old base intact.
- **Tiered lookups (LSM-style) to amortize rewrites.** Rewriting the whole base every 500 pairs
  gets slow as the base grows. Instead maintain two layers: a large **base** FST and a small
  **recent** FST. Batches merge into *recent* (cheap — it stays small); when *recent* exceeds a
  threshold (e.g. 1–10 MB), compact it into *base* once. Lookups check recent → base. This keeps
  per-batch merge cost bounded by the batch, not the corpus.
- **Raise the batch size.** With evaluation and dedup in-process, 500 is far too small. Make the
  commit trigger time- or size-based (e.g. every 30 s or every 50k new keys) and tune empirically.

## Milestones

**M1 — Library extraction.** Move the evaluator out of `src/bin/compute/` into the crate library
(`src/evaluator.rs`), keeping the thin CLI. Add unit tests pinned to the ruby evaluator's outputs
(the 9-form parity set already verified, plus edge cases: `R(u,x,0)`, overflow errors).

**M2 — Rust exploration engine.** Port pair enumeration, candidate templates, and chain-file I/O
from `explorer.rb` into an `explore` binary. Implement the three-tier dedup gate and
subexpression write-back. Reuse `state/chains/` and `state/progress.json` formats so existing
tooling and the ruby REPL keep working. Verify parity: run old and new engines from the same seed
state and diff the resulting FSTs (`ls_eval` dumps).

**M3 — Atomic incremental commits.** In-process delta build + union merge + atomic rename;
checkpoint-after-commit ordering; batch trigger tuning. Delete the now-unused per-batch subprocess
merges from the hot path (the standalone binaries stay for manual use).

**M4 — Tiered FSTs.** Add the recent/base layering with a compaction step and a
`fst/MANIFEST.json` naming the live layers. Update `load_evaluations` /
`query_evaluations_fst` / `ls_eval` to read through the layers.

**M5 — Cleanup & instrumentation.** Retire `candidates/*.txt` as an interchange format (in-memory
batches replace them; keep an optional debug dump). Emit per-batch stats (pairs/s, dedup hit rate,
evaluations, merge ms) so regressions are visible. Document the resume invariant in the doc header
of the `explore` binary.

## Invariants to uphold (test these)

1. **Idempotent restart:** killing the engine at any point and restarting produces byte-identical
   FSTs to an uninterrupted run.
2. **Exactly-once pairing:** across a full depth, each `(unary, nullary)` pair is enumerated once
   (assertable by counting pairs vs. chain-file lengths).
3. **Evaluate-once:** the number of actual evaluations in a run equals the number of new keys
   merged (dedup hit rate accounts for the rest).
4. **Ruby parity:** for any form, `evaluate_recursive_form` agrees with the ruby evaluator.

## Open questions

- **u64 ceilings.** Deep forms will overflow u64 quickly (the FST value type is u64). Decide policy:
  store an overflow sentinel, cap exploration when values exceed a bound, or move values out of the
  FST into a sidecar keyed by FST-assigned ids (FST maps to id; sidecar holds bignums via
  `num-bigint`, already a dependency).
- **Semantic dedup.** Distinct strings with equal values are both kept today (intentional — the map
  is expression → value). If the interesting output is min-length-per-value, a small inverted index
  (value → shortest expression) maintained at commit time would answer that without scanning.
- **Chain file growth.** Depth files grow combinatorially. The dedup gate slows this, but at some
  depth the frontier itself won't fit comfortably; consider storing frontiers as FSTs too (ordered,
  compressed, streamable) rather than plain text.
